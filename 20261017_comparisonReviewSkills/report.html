Code review skills: built-in vs own

/code-review (built into Claude Code 2.1.302, default level “high”) compared with /reviewBranch (own skill). 2 repositories, 4 branches, 2 runs per skill and branch = 16 reviews. Model Opus 5.5. 17–18 Oct 2026.

Recommendation: use both skills. Use /reviewBranch on every branch. Add /code-review on safety-relevant code and before each release. /reviewBranch gives a short list that you can trust, but it misses important bugs. /code-review finds the important bugs, but more than half of its list is noise. The two skills cost the same.

What we found

  1. /reviewBranch is precise. 10 of its 11 findings are real. It reported no false finding. When it finds a bug, its severity is the same as the owner’s.
  2. /reviewBranch misses bugs. It did not find the safety-gate bug in 4 of 4 runs. In 3 runs it examined that code and said it was correct. In 3 of 4 runs on the HR tool, it said “mergeable” while a known bug was present.
  3. /code-review finds more. It found every known bug that either skill found, in every run. It reported 31 real findings. /reviewBranch reported 10.
  4. /code-review is noisy. 35 of its 71 findings are weak, and 5 are false. At the default level, it does not check its findings. A person must sort the list.
  5. Cost is not a reason to choose. Each review costs $0.50–$1.79. The difference between the skills is in the noise.

What to do

Now

  • Run /reviewBranch on every branch. Fix what it reports.
  • On safety-relevant code (HR tool, file handling, approvals) and before each release, also run /code-review. Sort its list before you act. Expect about half to be noise.
  • Do not trust a “mergeable” verdict alone on safety-relevant code.

Next

  • Add the removed-behaviour check from /code-review to /reviewBranch: for each check that the branch removes or bypasses, name what it protected and find where the new code protects it again. This check found the safety-gate bug.
  • Measure the other levels of /code-review (“low” to “max”, and “ultra”). We do not know their noise yet.
Decision for the owner. The rule that we fixed before the test selects /reviewBranch, because /code-review is below the 50% precision limit. The rule does not count missed bugs. Do you want the next round to include “finds the known high-impact bugs” as a criterion?
