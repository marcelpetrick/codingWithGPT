What does the Ollama install script actually do?

A reading of curl -fsSL https://ollama.com/install.sh | sh, written for someone who writes software and wants to know what they're about to run as root.

Script fetched 2026-09-29 (release v0.34.4) 455 lines, POSIX sh sha256 25f64b810b947145095956533e1bdf56eacea2673c55a7e586be4515fc882c9f Local copy: install.sh

The script changes over time. Everything below describes the copy with the hash above, and line numbers (L123) point into it. Other versions may differ.

In short: on Linux it does eight things
  1. Works out your CPU architecture (amd64 or arm64) and whether you're on WSL2.
  2. Downloads a ~1.4 GB archive and unpacks it as root into /usr/local. The archive holds the ollama binary plus its GPU runtime libraries.
  3. Creates a system user and group called ollama, with its home (and model store) at /usr/share/ollama.
  4. Adds you to the ollama group, and adds the ollama user to render/video so it can use the GPU.
  5. Writes /etc/systemd/system/ollama.service, enables it at boot, and (re)starts it as the script exits. The API then listens on 127.0.0.1:11434.
  6. If it finds an AMD GPU, it downloads another ~1 GB of ROCm libraries.
  7. If it finds an NVIDIA GPU with no working driver, it adds NVIDIA's package repository and signing key to your package manager (on Debian, Ubuntu, RHEL, Rocky, Fedora and Amazon Linux only), installs cuda-drivers and kernel headers, builds the DKMS module and loads it.
  8. On macOS it's much simpler: it replaces /Applications/Ollama.app and symlinks the CLI into /usr/local/bin.

It asks for sudo for everything that writes outside your home directory. The downloads themselves run as you: curl is unprivileged, and only the tar at the end of the pipe runs as root. Full list below.

How curl | sh works

curl writes the script to stdout, and sh reads its program from stdin. Nothing is saved to disk, so there's no file to look at afterwards. The flags matter:

FlagMeaningWhy it's here
-ffail on HTTP ≥ 400Without it, a 404 or 500 error page would be piped into sh and run as a shell script.
-ssilentNo progress meter mixed into the output.
-Sshow errors anywayUndoes the part of -s that would hide errors.
-Lfollow redirectsNeeded: ollama.com/install.sh redirects to a GitHub release asset (release-assets.githubusercontent.com), which is what we observed when fetching it.

The main() wrapper protects against truncated downloads

A shell running a script from a pipe executes each command as soon as it has read it. If the connection dropped halfway through, a plain script would run its first half and stop at an arbitrary point, for example after deleting the old install but before unpacking the new one. So the whole script is one function body (main() { … }, L7–L453), and the only top-level command is the final main on L455. The shell can't run anything until it has read the closing brace, and if the download is cut short, the call never arrives and nothing runs.

How can sudo ask for a password when stdin is the script?

sudo doesn't read the password from stdin. It opens the controlling terminal (/dev/tty) directly, so the prompt still works while stdin is the pipe from curl. The script never escalates in one go. It sets SUDO=sudo when you're not root (L110–L118) and puts $SUDO in front of each privileged command. After you enter the password once, sudo's credential cache (15 minutes by default) covers the rest.

What's not there: integrity checks

Nothing in the script checks a checksum or signature. The only integrity guarantee is TLS to ollama.com and GitHub. That's the same trust you'd place in the release page, but it's worth knowing that nothing further is checked. Also, a pipeline's exit status is the status of its last command. For curl | zstd -d | sudo tar -x (L146–L148), set -e only sees tar. A truncated stream usually still fails, because zstd and tar both detect the unexpected end of file, but that's a side effect rather than a design.

Walkthrough

Preamble (L9–L42) user

  • set -eu: exit on the first failing command, and treat unset variables as errors. That's why optional variables are written ${OLLAMA_VERSION:+…} and ${OLLAMA_NO_START:-}.
  • tput … 2>&- gets the terminal's colour codes and closes stderr, so a missing tput or a dumb terminal stays silent.
  • mktemp -d plus trap cleanup EXIT is the standard temp-dir pattern. But the trap gets overwritten later.
  • require returns the names of missing tools as a string, so the script can list them all at once instead of failing on the first.
  • uname -m is mapped to Go-style architecture names (x86_64→amd64, aarch64|arm64→arm64). Anything else is rejected, including 32-bit ARM and x86.
  • OLLAMA_VERSION=0.x.y becomes a query string ?version=0.x.y appended to every download URL (L42).

macOS (L48–L93)

This branch never touches system services or users. It pkills a running Ollama, rm -rfs /Applications/Ollama.app, unzips the new app into place, and symlinks /usr/local/bin/ollama to the binary inside the bundle. It tries each write without sudo first and falls back to sudo only when that fails (cmd 2>/dev/null || sudo cmd, L81–L83). On most Macs /Applications is writable by admin users, so often the only password prompt, if there is one, is for /usr/local/bin. Finally open -a Ollama --args hidden launches the menu-bar app, unless OLLAMA_NO_START is set.

Linux preflight (L99–L127) user

The script tells WSL1 from WSL2 by the kernel release string (…microsoft-standard-WSL2). WSL1 has no real Linux kernel, so it's refused. id -u decides whether $SUDO is empty (you're root) or sudo. The comment on L112 says “Running as root” inside the branch that runs when you are not root, so it's the wrong way round. The code itself is correct.

Choosing where to install (L159–L162)

for BINDIR in /usr/local/bin /usr/bin /bin; do
    echo $PATH | grep -q $BINDIR && break || continue
done
OLLAMA_INSTALL_DIR=$(dirname ${BINDIR})

The script takes the first of three candidates that appears in your $PATH, and the install prefix is its parent directory. On almost every system that means BINDIR=/usr/local/bin and prefix /usr/local. The archive's contents land in /usr/local/bin/ollama and /usr/local/lib/ollama/…. The binary finds its libraries relative to its own location, which is why the prefix layout matters.

Installing (L164–L176) sudo

  • An existing lib/ollama is removed completely first (rm -rf). Its versioned GPU libraries would otherwise mix with the new ones. The old binary is simply overwritten by tar.
  • install -o0 -g0 -m755 -d creates bin/ and lib/ollama/ as root:root 0755 if they don't exist.
  • download_and_extract first sends a HEAD request for the .tar.zst file. If it exists, the script needs zstd and fails with install hints if you don't have it. Otherwise it falls back to .tgz (for old versions; the current .tgz URL returns 404). The data flows curl (you) → zstd -d (you) → sudo tar -xf - -C /usr/local (root).
  • Jetson (/etc/nv_tegra_release exists): an extra bundle for JetPack 5 (R35) or 6 (R36) is unpacked over the base install.

The systemd service (L197–L252) sudo

This runs only if systemctl is installed at all. It sets up:

  • useradd -r -s /bin/false -U -m -d /usr/share/ollama ollama: a system account (low UID, no aging) with no login shell, a matching group, and a home directory. The home matters because the server stores models in ~/.ollama/models, so the model store ends up at /usr/share/ollama/.ollama/models. On many systems /usr sits on the root partition, so tens of gigabytes of weights can fill /.
  • ollama is added to render and video if those groups exist. Those groups own /dev/dri/* and, on AMD, /dev/kfd, the GPU device nodes.
  • You are added to the ollama group ($(whoami), the unprivileged caller). This only takes effect at your next login. You don't need it to use the CLI, which talks to the server over HTTP.

The unit it writes:

[Unit]
Description=Ollama Service
After=network-online.target

[Service]
ExecStart=/usr/local/bin/ollama serve
User=ollama
Group=ollama
Restart=always
RestartSec=3
Environment="PATH=…your $PATH at install time…"

[Install]
WantedBy=default.target
  • Your current $PATH is baked into the unit. The heredoc expands it at install time, so any personal directories on your PATH, such as ~/bin, ~/.cargo/bin or a venv, end up in a system service.
  • After=network-online.target without Wants=network-online.target only orders the start. It doesn't pull the target in, so on many systems it has no effect.
  • Restart=always: the server comes back 3 seconds after any exit, including a crash or a kill. To actually stop it, use systemctl stop.
  • WantedBy=default.target: it starts at every boot.
  • No OLLAMA_HOST is set, so the server binds only to loopback (127.0.0.1:11434). Setting it (for example 0.0.0.0) exposes an unauthenticated API to the network.
  • There's no sandboxing (ProtectSystem=, NoNewPrivileges=, …). The service runs as an ordinary unprivileged user and nothing more.

The script decides whether systemd is actually running with systemctl is-system-running: running or degraded both count. In containers, or on WSL2 without systemd enabled, you get a warning and no service. If it is running, daemon-reload and enable happen immediately, but restart is deferred to the EXIT trap (L238–L239). It therefore runs after the GPU driver work, whichever way the script exits.

GPU detection (L271–L303)

The script checks in this order:

  1. Is nvidia-smi installed? Then it assumes the driver works, prints “NVIDIA GPU installed.” and exits. It doesn't check that the driver is new enough.
  2. Otherwise it looks for PCI vendor IDs: lspci -d 10de: (NVIDIA) or 1002: (AMD). If lspci is missing it tries lshw -c display -numeric, which runs under sudo because lshw reports incomplete information without root.
  3. With neither tool installed, it can't tell, so it warns and exits. Your GPU might still work, but no drivers get installed.

AMD (L305–L311) sudo

The only step is unpacking ollama-linux-amd64-rocm.tar.zst (~1.05 GB) into the same prefix. It adds ROCm userspace libraries under lib/ollama. The kernel driver (amdgpu) is part of the mainline kernel, so the script leaves it alone. It doesn't check whether your specific GPU is supported by ROCm either. If both an NVIDIA and an AMD GPU are present and nvidia-smi is missing, the AMD branch runs and the script exits without installing an NVIDIA driver.

NVIDIA without a driver (L313–L449) sudo

This is the invasive part, and it only runs on a machine with an NVIDIA GPU and no working nvidia-smi. It follows NVIDIA's own CUDA installation guide:

  • apt (Debian/Ubuntu): downloads cuda-keyring_1.1-1_all.deb into the temp dir and installs it with dpkg -i. From then on your system trusts NVIDIA's repository signing key for all future apt updates. On Debian it also enables contrib by writing /etc/apt/sources.list.d/contrib.list, derived with sed 's/main/contrib/'. It then runs apt-get update and apt-get -y install cuda-drivers, with DEBIAN_FRONTEND=noninteractive passed through sudo -E. The -E is needed because sudo clears the environment by default.
  • dnf/yum (RHEL, CentOS, Rocky, Fedora, Amazon Linux): adds NVIDIA's .repo file (and EPEL on RHEL), then runs install cuda-drivers, plus nvidia-driver-latest-dkms on CentOS or RHEL 7. Fedora 39 and later always get the fedora39 repo. Amazon Linux is mapped to fedora37.
  • Kernel module (if nvidia or nvidia_uvm isn't loaded): installs kernel headers for the running kernel, runs dkms install for any module that is only “added”, then modprobe nvidia nvidia_uvm. If the open-source nouveau driver is loaded it holds the GPU, so the script asks you to reboot and exits.
  • Persistence: if nvidia-persistenced exists, nvidia and nvidia-uvm are added to /etc/modules-load.d/nvidia.conf so they load at boot. The grep -qxF check makes this safe to repeat.

The architecture in NVIDIA's repo URLs is uname -m with aarch64 rewritten to sbsa, NVIDIA's name for server ARM.

Why | sudo tee file and not sudo … > file?

Your (unprivileged) shell performs the redirection before sudo even starts, so sudo echo x > /etc/foo fails with “Permission denied”. Piping into sudo tee makes a root process open the file. The script uses this pattern for every write under /etc. The reverse also holds: in $SUDO sed … < /etc/apt/sources.list (L369) your own shell opens the input file, so the sudo in front of sed does nothing. That's harmless, because those files are world-readable.

Running it as root instead (… | sudo sh)

That works too ($SUDO stays empty), with side effects. $(whoami) becomes root, so root joins the ollama group rather than you. $PATH is sudo's secure_path, which is arguably a cleaner value for the unit file. And every command, including the downloads, runs as root.

What's in the 1.4 GB download

We streamed ollama-linux-amd64.tar.zst through tar -tv without writing it to disk. The full listing is in ollama-linux-amd64.contents.txt. It has 62 files and symlinks, 2.24 GB unpacked, and every entry is owned by root/root. So although root's tar preserves the owners recorded in the archive, they end up root:root, which is what you want.

The server doesn't do the maths itself: it starts runner processes backed by these ggml/llama.cpp libraries.

Quirks and edge cases

These come from reading the code. Quirks 1, 2, 3 and 5 are also reproduced, using the script's own logic, by verify_quirks.sh, which needs no root and passes under sh and bash. The rest are from reading only. Most are harmless, and none of them affect a typical Ubuntu or Fedora install.

1. The cleanup trap is overwritten, so the temp dir is left behind

trap replaces the handler; it doesn't add to it. L20 installs cleanup, L193 replaces it with install_success, and L239 (systemd hosts) replaces that with start_service. As a result, the mktemp -d directory is never removed once the script gets past L193. It's empty, except on the apt path where it holds cuda-keyring.deb. On systemd hosts the success banner also isn't printed on some paths. For example, when nvidia-smi exists, you only see “NVIDIA GPU installed.”

2. The “Unknown package manager” check can never trigger

PACKAGE_MANAGER=
for PACKAGE_MANAGER in dnf yum apt-get; do
    if available $PACKAGE_MANAGER; then break; fi
done
if [ -z "$PACKAGE_MANAGER" ]; then error "Unknown package manager…"; fi

After a shell for loop ends without break, the loop variable keeps its last value (apt-get), so it's never empty. The script then continues, reaches case $OS_NAME … *) exit ;; for any unlisted distribution, and exits silently with status 0. On Arch, Manjaro, openSUSE, Gentoo and others, an NVIDIA machine without a driver gets a working CPU install and no message saying it has no GPU support. On those distributions, use the distro packages (on Arch/Manjaro: ollama, ollama-cuda, ollama-rocm).

3. The symlink step is dead code on normal systems, and harmful when BINDIR=/bin

L173 compares $PREFIX/bin/ollama with $BINDIR/ollama. With /usr/local/bin or /usr/bin they're the same string, so the link is skipped. With /bin, which is also the fallback when none of the three candidates matches because the loop variable keeps its last value, the prefix is /. Then "//bin/ollama" != "/bin/ollama", and L175 runs ln -sf //ollama /bin/ollama, replacing the freshly unpacked binary with a symlink to a nonexistent /ollama. The link target ($PREFIX/ollama, with no bin/) looks like a leftover from an older archive layout. This needs an unusual $PATH to trigger.

4. PATH matching is a substring grep

echo $PATH | grep -q /usr/local/bin also matches /opt/x/usr/local/bin or /usr/local/bin2. In practice this only changes which prefix is picked in exotic setups.

5. Rocky Linux 10 gets the wrong repository

For Rocky the major version is taken with cut -c1, the first character of the version (L407). For 10.0 that gives 1, so the script looks for a rhel1 repo, the HEAD check fails, and it stops with “not supported by NVIDIA”. RHEL and CentOS use cut -d . -f 1 and are fine.

6. nvidia-smi present means “done”

If the binary exists, the script assumes the driver works. It doesn't check that the driver is recent enough for the CUDA runtime bundled in the archive, and doesn't even check that nvidia-smi runs successfully. An old driver shows up later as Ollama falling back to the CPU.

7. Re-running it restarts the server

The documented upgrade path is to run the same command again. That overwrites the unit file (losing any direct edits), deletes and replaces lib/ollama, and ends with systemctl restart ollama, which unloads models and cuts off any requests in flight. On a shared box, schedule it.

8. The Debian contrib derivation is crude

sed 's/main/contrib/' replaces the first “main” on each line, wherever it appears, and ignores sources.list if it doesn't exist. On a Debian system that only has debian.sources (deb822 format, standard since Debian 12), the pipeline creates an empty contrib.list and a separate contrib.sources copy. It works, but it leaves clutter.

9. Not really POSIX

local (L24, L131) isn't in POSIX. It works in dash, bash, busybox ash and zsh's sh mode, which covers every /bin/sh you're likely to meet.

Knobs

Running it more carefully

# 1. download, don't pipe
curl -fsSL https://ollama.com/install.sh -o install.sh
# 2. read it (or diff it against the copy next to this page)
less install.sh
sha256sum install.sh
# 3. run it, pinned to a version you know
OLLAMA_VERSION=0.x.y sh install.sh

Alternatives that avoid running a script as root: your distribution's package, the official Docker image (ollama/ollama), or unpacking the archive by hand into a prefix you own and running ollama serve yourself. The last option skips the user, the service and the driver steps entirely.

Undoing it

sudo systemctl disable --now ollama
sudo rm /etc/systemd/system/ollama.service
sudo systemctl daemon-reload
sudo rm /usr/local/bin/ollama
sudo rm -r /usr/local/lib/ollama
sudo rm -r /usr/share/ollama        # deletes all downloaded models
sudo userdel ollama
sudo groupdel ollama                # if userdel didn't already
sudo gpasswd -d "$USER" ollama      # only if the group still exists

If the NVIDIA path ran, the driver, the DKMS module, the NVIDIA repository and its key, and /etc/modules-load.d/nvidia.conf all stay. Remove them with your package manager if you don't want them.
