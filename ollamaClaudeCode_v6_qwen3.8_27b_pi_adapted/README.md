## Verdict (2026-11-18, n=3, round closed)

**Yes, it works here, and by the fixed rule it is the most correct model on the box. It is also about 4× slower than the champion.**
Use `claude-ol-qwen3.8_27b_pi` when correctness matters more than time: Qt/C++, multi-file fixes, GitLab
state changes. Keep `claude-ol-kat` for fast, interactive work. The default alias did not change. That is the owner's decision.

Report with charts: [`report.html`](report.html), generated by `make_report.py` from the result files.

- **pi vs KAT:** +8.5 points, which is more than the 3-point tie band. Session by session, pi scored higher in 7 pairs, KAT in 1, and 1 was a tie. A sign test gives p ≈ 0.07, so the result is clear but not proven at 5%.
- **The medians hide some spread.** pi lost checks in 3 of 9 sessions: 17/18, 13/14 (a 600 s timeout) and 14/15. KAT lost checks in 7 of 9 sessions.
- **The adapter helps, but only a little in correctness.** pi is +3.3 points over its own base, just above the tie band. The clearer effect is in the agent behaviour: 32% fewer tool calls (17 vs 25) and 36% shorter sessions (560 vs 879 s). The base hit the 600 s limit twice; pi hit it once. This matches the direction of the card's claim (−55 to −64% tool calls), but the effect here is smaller.
- **Speed is the cost.** It is a dense 27B model: 20 tok/s at 150k context (30.8 tok/s at short context) and 1,060 tok/s prefill. KAT does 70 and 2,985. The prompt cache works (a repeat prefill takes 0.3 s).
- **Context window: 200k, the same usable size as KAT.** The alias caps Claude Code at 180k, because past 200k the model silently halves the context. At 150k a first prefill takes about 2.5 min (KAT: about 50 s). Repeat turns use the prompt cache.
- **The misses are real.** The transcripts show real omissions, for example a created issue without `--assignee erin`, which the notes asked for. They are not grader errors.

### Why the merge, and what it costs

The full account is in [`MERGE_ON_THIS_MACHINE.md`](MERGE_ON_THIS_MACHINE.md).

The card's own merge (`PEFT merge_and_unload` on the BF16 checkpoint) needs about 110 GB of disk and
about 54 GB of RAM. The laptop has 25 GiB free on `/home`, 30 GiB on `/` and 32 GB of RAM.
`llama-export-lora` writes F16 (54 GB). So `merge_lora_inplace.py` adds `2.0 · B·A` to each Q8_0
tensor and quantizes it again to Q8_0. The byte size stays the same, so it overwrites the base file.
Both arms then go through the same `llama-quantize` Q8_0 → Q4_K_M, so the adapter is the only difference.
The LoRA covers FFN in all 64 blocks and q/k/v/o in the 16 full-attention blocks, not the SSM layers.

### Why thinking must be forced off

A capture of Claude Code 2.1.327 shows that each request carries `output_config.effort: high`, also
with `CLAUDE_CODE_DISABLE_THINKING=1` or `MAX_THINKING_TOKENS=0`. Ollama maps that to thinking on.
The adapter was trained with thinking off. The tags therefore use renderer `qwen3.8` with parser
`qwen3-coder`. That parser has no thinking support, so the tag has no thinking capability. Ollama then
drops the thinking request from Claude Code and renders with think=false.

## The rule (fixed before the data)

The round 11-02 rule applies unchanged (`../ollamaClaudeCode_v4_tielCoder/ROUND_2026-11-02.md`, "The rule"):
correctness = mean over four tasks of the median share of checks; T5 ≥ 7/8 or not ranked; n=3
final; a session stops at 600 s and keeps the score of its final state.

The recommendation to the owner follows from these numbers:

1. **Use it as the default** if T5 ≥ 7/8 and its correctness is more than 3 points above KAT in this arm.
2. **Keep it as an extra alias** if T5 ≥ 7/8 and its correctness is within 3 points of KAT.
3. **Do not use it** in every other case.
4. **The adapter works in Ollama** only if pi beats the base by more than 3 points of correctness, or wins T5. Otherwise the adapter adds nothing here.
